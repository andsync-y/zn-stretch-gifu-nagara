# 施策A セットアップ手順書（オーナー作業）

`docs/capi-offline-events.md` のチェックリストを、画面の操作単位まで落としたもの。
上から順にやれば終わる。**所要時間の目安：40分**（Meta 10分／Google 20分／GitHub 5分）。

作業する場所は3つ：**Metaイベントマネージャ** → **Google Cloud** → **GitHubのSecrets**。

## Part 1：Meta側（10分）

### Step 1. データセットIDを用意する

> **重要**：Metaは「ピクセル」と「データセット」を統合済みで、**今あるピクセルIDが
> そのままデータセットID**として使える。新しく作る必要はない。
> Webの行動もオフラインの成約も同じデータセットに入れるほうが、Metaが両方をまとめて
> 学習するので有利。

1. [business.facebook.com/events_manager](https://business.facebook.com/events_manager) を開く
2. 左メニュー **「データソース」** をクリック
3. 一覧に「全力ストレッチ岐阜長良店」のデータセット（旧ピクセル）があるはず。クリックする
4. 名前の下、または右上に **15〜16桁の数字**が出ている。これがデータセットID
   - 見つからないときは右上の **「···」→「設定」**。ページ上部に「データセットID」がある
5. **この数字をメモ**（あとで `META_DATASET_ID` に入れる）

<details>
<summary>データセットが1つも無い場合（新規作成する）</summary>

1. 「データソース」→ **「データソースをリンク」**（または「+ 追加」）
2. **「ウェブ」** を選び、名前は `全力ストレッチ岐阜長良店` として作成
3. 接続方法を聞かれたら **「コンバージョンAPI」** を選ぶ（コードは既に入っているので
   「手動で設定」でよい）
4. 作成後に表示されるIDをメモ

</details>

> このIDは、サイトに入っている `PUBLIC_META_PIXEL_ID`（Vercelの環境変数）と**同じ値**に
> なるのが正常。違う値なら、どちらが本番で使われているデータセットか確認すること。

### Step 2. Conversions APIのアクセストークンを生成

1. Step 1 のデータセットを開いた状態で、上部タブの **「設定」** をクリック
2. 下へスクロールして **「コンバージョンAPI」** セクションを探す
3. **「アクセストークンを生成」** をクリック
4. 長い文字列（200文字前後）が表示される

> ⚠️ **このトークンは1度しか表示されない。** 画面を閉じる前に、
> そのままGitHubのSecretsに貼り付けてしまうのが確実（Part 3 を先にやってもよい）。
> 消してしまったら、同じ画面でもう一度生成すればよい（古いトークンは無効になる）。

### Step 3. 広告アカウントとの紐づけを確認

1. 同じ「設定」タブ内の **「関連アセット」**（または「ビジネスアセット」）を見る
2. 広告アカウントが紐づいていればOK。無ければ **「アセットを追加」** →
   広告アカウントを選択
3. Step 1 で既存ピクセルを使う場合、**すでに紐づいているはず**なので確認だけでよい

## Part 2：Google側（20分）

Driveの電話ハッシュマスタを読むための「ロボット用アカウント」を作る作業。

### Step 4. GCPプロジェクトを用意してDrive APIを有効化

1. [console.cloud.google.com](https://console.cloud.google.com/) を開く
   （**Driveフォルダを持っているGoogleアカウント**でログインすること）
2. 画面上部のプロジェクト選択（「プロジェクトを選択」）→ **「新しいプロジェクト」**
   - プロジェクト名：`zn-stretch-kpi` など分かる名前
   - 作成後、そのプロジェクトが選択されている状態にする
3. 左メニュー **「APIとサービス」→「ライブラリ」**
4. 検索窓に **`Google Drive API`** と入力 → 出てきたものをクリック
5. **「有効にする」** ボタンをクリック

> ✅ 確認：「APIとサービス」→「有効なAPI」に Google Drive API が並んでいればOK。

### Step 5. サービスアカウントを作成してJSONキーを取る

1. 左メニュー **「APIとサービス」→「認証情報」**
   （または「IAMと管理」→「サービスアカウント」）
2. 上部 **「+ 認証情報を作成」→「サービスアカウント」**
3. 入力：
   - サービスアカウント名：`kpi-drive-reader`
   - サービスアカウントID：自動で入る
   - **「作成して続行」**
4. 「このサービスアカウントにプロジェクトへのアクセスを許可」→ **何も選ばず「続行」**
   （Driveへの権限はGCPのロールではなく、Step 6 のフォルダ共有で与えるため）
5. 「ユーザーにこのサービスアカウントへのアクセスを許可」→ **「完了」**
6. 一覧に戻るので、作ったサービスアカウントをクリック
7. **「キー」タブ → 「鍵を追加」→「新しい鍵を作成」→ 「JSON」→「作成」**
8. **JSONファイルが自動でダウンロードされる**（`zn-stretch-kpi-xxxxx.json` のような名前）

> ⚠️ このJSONファイルは再ダウンロードできない。無くしたら新しい鍵を作り直す。
> 用が済んだらPCから削除してよい（GitHub Secretsに入れれば十分）。

9. **サービスアカウントのメールアドレスをコピー**しておく
   （`kpi-drive-reader@zn-stretch-kpi.iam.gserviceaccount.com` のような形）。
   Step 6 で使う。

### Step 6. Driveフォルダをサービスアカウントに共有

1. Googleドライブで **「32_顧客電話_マスタ」** フォルダを開く
2. フォルダを右クリック → **「共有」**
3. Step 5 でコピーした **サービスアカウントのメールアドレスを貼り付け**
4. 権限を **「閲覧者」** にする（編集権限は不要）
5. **「通知を送信」のチェックを外す**（ロボット宛なのでメールは届かない）
6. **「共有」** をクリック

> ✅ 確認：共有相手の一覧にサービスアカウントのメールが「閲覧者」で並んでいればOK。
> フォルダIDが `1Gsa1G7n4OHTNRcz8QW6GxSp-T52v4H3p` と一致しているかも確認する
> （URLの `/folders/` の後ろの文字列）。違う場合は教えてください。コード側を直します。

## Part 3：GitHubにSecretsを登録（5分）

1. [リポジトリのSecrets設定](https://github.com/andsync-y/zn-stretch-gifu-nagara/settings/secrets/actions)
   を開く（Settings → Secrets and variables → Actions）
2. **「New repository secret」** を3回押して、次の3つを登録する

| Name（そのままコピー） | Secret に入れる中身 |
|---|---|
| `META_DATASET_ID` | Step 1 の数字だけ（`123456789012345`）。引用符や空白を入れない |
| `META_CAPI_ACCESS_TOKEN` | Step 2 の長い文字列をそのまま |
| （`ZN_SYSTEM_USER` / `ZN_SYSTEM_PASS`） | 店舗システムのログイン情報。週次KPIジョブ用に**登録済み**なので追加作業は不要 |
| `GDRIVE_SA_KEY` | Step 5 でダウンロードしたJSONファイルを**テキストエディタで開き、中身を全部コピーして貼り付ける**（`{` から `}` まで、改行もそのまま） |

> `GDRIVE_SA_KEY` のよくある失敗：
> - ❌ ファイルをアップロードしようとする → **中身のテキストを貼る**のが正解
> - ❌ 改行を消して1行にする → **そのままでよい**。JSON内の `\n` は消さない
> - ❌ 前後に余計な空白や引用符を足す → **不要**

> ✅ 確認：3つとも一覧に並び、更新日時が今日になっていればOK（値は二度と表示されない）。

## Part 4：電話帳（phone-book.json）の作り方

回数券をいつ・いくらで買ったかは、店舗システムの来店記録から**自動で取れる**（2026-08-20）。
足りないのは「**店舗システムの顧客ID ↔ 電話番号**」の対応だけ。これを電話帳と呼ぶ。

- 置き場所：Driveフォルダ「**32_顧客電話_マスタ**」の **`phone-book.json`**（1ファイルに積み上げる）
- 中身：顧客IDと、電話番号の**SHA256ハッシュ**だけ。生の番号は入れない

```json
{
  "note": "顧客ID → 電話番号のSHA256。生の電話番号は含まない。",
  "records": [
    { "customer_id": "10000001", "phone_hash": "0ad07193…（64桁）" }
  ]
}
```

### 大前提：顧客IDはファイル名で渡す

サロンボードの画面には**店舗システムの顧客IDが写っていない**（顧客IDは店舗システム独自の採番のため）。
そこで、**スクショのファイル名の先頭を顧客IDにする**運用にしてある。

```
10000001.png          ← これでOK
10000001_yamada.jpg   ← 先頭が顧客IDならこれでもOK
IMG_1234.png          ← ✕ 顧客IDが分からないのでスキップされる
```

顧客IDはActionsの実行サマリーに一覧で出るので、それを見ながら保存すればよい。

### 方法A：Coworkに任せる（通常はこちら）

Coworkの定期タスク **「顧客電話帳の更新（スクショ→顧客ID×電話ハッシュ）」**（毎月2日 9:00）が、
取込フォルダのスクショを読んで `phone-book.json` に**追記**する。設定は更新済みなので、
オーナーがやることは次の4ステップだけ。

1. Actions →「Meta CAPIオフラインイベント送信（月次）」の実行サマリーを開く
2. **「📞 電話番号の登録が必要な顧客」** に並んだ顧客IDを控える（無ければ何もしなくてよい）
3. その顧客IDを店舗システムで開いて氏名を確認 → サロンボードの顧客情報ページで電話番号をスクショ
4. **ファイル名を顧客IDにして**、Drive「**31_顧客電話_取込**」へ入れる

**1顧客につき生涯1回**でよい。顧客IDは自動採番なので、一度登録すればその顧客の次回以降の
回数券購入は自動で送信される。月を追うごとに作業は減っていく。

### 方法B：まとめて一気に作る（初回の立ち上げ向き）

初回は登録すべき人が数十人になるので、スクショより表にまとめたほうが早い。
**自分のPCで**次を実行する（生の電話番号がネットに出ない）。

1. 表計算ソフトで「顧客ID, 電話番号」の2列を作り、CSVで保存する（見出し行はあってもなくてもよい）

   ```
   顧客ID,電話番号
   10000001,090-1234-5678
   10000002,09087654321
   ```

2. リポジトリを手元に置いて、次を実行する

   ```bash
   node scripts/make-phone-book.mjs phone-input.csv
   ```

   すでに `phone-book.json` がある場合は、2つめの引数に渡すと**追記**になる（既存は消えない）。

   ```bash
   node scripts/make-phone-book.mjs phone-input.csv phone-book.json
   ```

3. できた `phone-book.json` をDrive「32_顧客電話_マスタ」へアップロードする
4. **入力に使ったCSVは削除する**

このスクリプトは、番号を `090-1234-5678 → 819012345678 → SHA256` とMetaの規則どおりに正規化し、
**生の電話番号を出力にもログにも一切出さない**（報告は件数と行番号だけ）。
読めない番号は推測で埋めず、行番号を挙げてスキップする。
`.gitignore` で `phone-book.json` と `phone-*.csv` を無視しているので、誤ってコミットされることもない。

> どちらの方法でも、ファイル名は必ず `phone-book.json`。月ごとに分けない。

## Part 5：動作確認（3段階）

Secretsが揃ったら、この順で確認します。**いきなり本送信しないこと。**

### ① dry_run（送信しない・件数だけ見る）

1. リポジトリの **Actions** タブ →
   左の一覧から **「Meta CAPIオフラインイベント送信（月次）」**
2. 右の **「Run workflow」** →
   - `dry_run` は **チェックしたまま（true）**
   - `test_event_code` は **空**
3. **「Run workflow」** を実行 → 1〜2分待つ
4. 実行結果のログを開き、次を確認：
   - `- 「今年」= YYYY-MM-DD〜YYYY-MM-DD ... 有効 N件` → 来店記録CSVが取れているか
   - `Drive: phone-book N件` → **0件ならDriveの共有が効いていないか、電話帳が未作成**
   - `来店記録の成約: N件 → 電話帳と突合できた M件 / 未登録 K件` → 実感と合っているか
   - `送信対象イベント: N件 / 合計 ◯◯円` → 件数と金額が実感と合っているか
   - `dry_run のため送信しません` と出て正常終了していること

### ② テスト送信（Metaに届くか見る）

1. Metaイベントマネージャ → 該当データセット → **「テストイベント」** タブを開く
2. 画面に出ている **テストイベントコード**（`TEST12345` のような文字列）をコピー
3. Actions → 同じワークフロー → Run workflow →
   - `dry_run` の **チェックを外す（false）**
   - `test_event_code` に **コピーしたコードを貼る**
4. 実行 → **「テストイベント」タブに Purchase が並べば成功**（数秒〜1分で出る）
   - 各イベントをクリックすると、送った金額・時刻・`ph`（ハッシュ）が確認できる

> このテスト送信は**送信済みとして記録されません**。同じ成約を次の本送信で
> もう一度送れるので、安心して試せます。

### ③ 本送信

1. Actions → Run workflow →
   - `dry_run` の **チェックを外す（false）**
   - `test_event_code` は **空にする**
2. 実行 → ログに `本送信 完了（N件）` と出ればOK
3. 以降は **毎月3日 10:00（JST）に自動実行**される

> 反映確認：イベントマネージャの「概要」に出るまで**最大数時間**かかることがある。
> すぐ出なくても失敗ではない。

### 送信後にやること

送信が数ヶ月ぶん溜まったら（目安：Purchase が50件以上）、
Meta広告の広告セットで **最適化イベントを Purchase に変更**する。
これで初めて「回数券を買う客に似た人」への配信最適化が働きます。

## つまずいたときの見どころ

| ログに出るエラー | 原因と対処 |
|---|---|
| `GDRIVE_SA_KEY がJSONとして解析できません` | JSONの中身が途中で切れている。ファイルを開き直して全文を貼り直す |
| `Google認証に失敗 (400)` | サービスアカウントのキーが無効。Step 5 で新しい鍵を作り直す |
| `Drive files.list に失敗 (404)` | フォルダIDが違うか、Step 6 の共有ができていない |
| `phone-master_YYYY-MM.json も phone-book.json もありません` | 共有はできているがファイル名が違う。命名規則を確認 |
| `期間 … を覆えていない` | 来店記録の期間フィルタが変わった。「来店記録CSVの取得確認」を `inspect` で走らせて画面を確認する |
| `Meta CAPI 送信に失敗 (HTTP 400) ... code 190` | アクセストークンが無効・期限切れ。Step 2 で再生成 |
| `Meta CAPI 送信に失敗 (HTTP 400) ... Invalid parameter` | データセットIDが違う。Step 1 を確認 |
| 送信対象 0件 で終わる | 正常。マスタに `purchases` がまだ入っていない（Part 4 待ち） |

どれも**ワークフローが失敗（赤）で止まる**ので、数字が勝手に作られることはありません。
