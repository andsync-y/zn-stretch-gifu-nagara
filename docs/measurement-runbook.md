## 2. 残っている作業：LINEクリックをコンバージョンに入れる（施策C）

**これが施策Cで唯一残っている穴。** LINEは8/17のLP改修で予約導線の主役の一つに引き上げたのに、
Google広告の学習信号に入っていない。入れないと、Googleは「LINEで予約する人」を無視して
HPBをクリックする人だけに寄せて配信し続ける。

### 手順（2026-08-20 実施済み）

GA4側では `line_click` は**すでにキーイベント**になっていた。詰まっていたのはGoogle広告側だけ。

1. Google広告 → **目標 → 概要 → ＋新しいコンバージョンアクション**
2. データソース：**ウェブサイトで発生したコンバージョン**（GA4プロパティ 545472920 が連携済み）
3. **「リンクされたアカウントから複数のコンバージョンアクションを作成する」→ 選択**
4. `line_click` にチェック → カテゴリ **「お問い合わせ」**（= CONTACT / 画面によっては「連絡先」表記）

#### ⚠️ 手動ウィザードは保存に失敗する（2026-08-20 実測）

上記4まで進めて保存すると、**「新しいコンバージョンアクションが保存されませんでした」**で必ず失敗した。

| 試したこと | 結果 |
|---|---|
| 何度か再試行 | ✕ 毎回同じエラー |
| シークレットウィンドウ（拡張機能なし） | ✕ 同じ |
| カテゴリを「リードフォームの送信」に変更 | ✕ 同じ |

**回避策**：ウィザードの「コンバージョンの作成と測定」画面に、Google自身が出す
**「ユーザーがイベント line_click を完了するとインポートされます」という提案**が表示される。
その **「提案を承認」** ボタンから作成すると**通る**（手動保存とは別の処理経路のため）。

同じ症状が出たら、手動で粘らずに提案ボタンを探すこと。

#### カテゴリは「予約」にしない

`hpb_click` が「予約」カテゴリなので、同じにすると同一の目標グループにまとめられ、
**意図せず主要CVとして入札に効いてしまう**。「お問い合わせ／連絡先」なら別グループになる。

#### ⚠️ 作成しただけでは副次にならない（必ず作成後に確認する）

作成時のダイアログには「『連絡先（ウェブサイト）』はアカウントのデフォルトの目標ではありません」
と表示され、「サブアクション」のラジオボタンもグレーアウトして選べない。
**この表示を信用しないこと。** 実際に作られたアクションは、
**アカウントのデフォルト目標「連絡先」の中に「メイン」として**入っていた（＝入札に効く状態）。

作成後に必ず **目標 → 概要** で次を確認する。

1. 目標グループ（連絡先）の左肩に **「アカウントのデフォルト」** のラベルが付いていないか
2. 付いている場合、そのアクションの「アクションの最適化」列が **メイン** になっていないか

メインだった場合の直し方（2026-08-20 に実施済み・これで副次になった）:

1. コンバージョンアクション名のリンクを開く
2. **設定を編集** → **アクションの最適化**
3. **「入札単価の最適化に使わないサブアクション」** を選択して保存

※作成時はグレーアウトしていても、**作成後の編集画面では選べる**。

目標グループ自体を「その他の目標」へ移すのは不可。同じグループの `Clicks to call` の
扱いまで変わってしまうため、**個別アクションだけをサブにする**。

## 5.5 Microsoft Clarity（行動データ）

「数字は出ているのに、なぜ予約に至らないのか」を見るためのヒートマップ・セッション録画。
GA4が「何件起きたか」を答えるのに対し、Clarityは「どこで詰まっているか」を答える。

### タグ（設置済み）

`src/components/Clarity.astro` を `src/layouts/Base.astro` から読み込む。
Metaピクセル・GA4と同じ場所に並べてあり、**全32ページに出力される**。
読み込みは `t.async=1` の非同期で、表示速度には影響しない。
プロジェクトIDはクライアントに露出する公開タグIDなので直書き（GA4と同じ扱い）。

### 個人情報のマスク

**2026-08-20時点で、このサイトに訪問者の個人情報は表示されていない。**

| 要素 | 判断 |
|---|---|
| 店舗の電話番号 | 公開されている店舗情報。訪問者の個人情報ではないのでマスクしない |
| スタッフ氏名 | E-E-A-T強化のため意図的に公開している。マスクしない |
| クチコミ投稿者名 | **イニシャルのみ**（`N さん`）。それでも将来フルネームを貼られたときの保険として `data-clarity-mask="true"` を付与済み |
| 入力フォーム | **存在しない**（予約はホットペッパー＝外部ドメイン）。Clarityが入力値を記録する経路自体が無い |

マスク付与箇所：`src/pages/voice.astro` / `src/layouts/SymptomLayout.astro` / `src/pages/lp.astro`
のクチコミ投稿者名。**本文にはマスクを付けない**（公開されたクチコミであり、
読まれているかどうかを知りたいため）。

> クチコミ本文を編集するときは、`src/consts.ts` の `REVIEWS` に**フルネームを貼らない**こと。

### データ取得（clarity_7d.json）

`scripts/fetch-clarity-data.mjs` を `windsor-data.yml` から毎朝実行し、
`windsor-data` ブランチへ `clarity_7d.json` として置く。

**APIの性質**：Clarity Data Export API（`project-live-insights`）は
**「直近N日の集計」を返すのであって、日別の内訳は返さない**。
そのため1日1スナップショットとして積み上げ、**取得日（JST）をキーに重複排除**する。

```
{
  "note": "...",
  "fetched_at": "2026-08-20T...Z",
  "no_data": false,            // 7日分のどれか1日でもデータがあれば false
  "latest_data_date": "2026-08-20",
  "days": [
    { "date": "2026-08-20", "num_of_days": 3, "no_data": false,
      "metrics_available": ["Traffic", "ScrollDepth", ...],
      "overall": { "ok": true, "data": <APIレスポンスそのまま> },
      "by_page_device": { "ok": true, "data": <APIレスポンスそのまま> } }
  ]
}
```

**指標はAPIが返すものをそのまま入れる。無い指標は作らない。**
2026-08-20時点でこの実行環境から `learn.microsoft.com` に到達できず、公式ドキュメントで
レスポンス形式を照合できていない。そのため**形を仮定せずに生のまま保存する**設計にしてある。
形が変わっても壊れず、中身は後から読み替えられる。

### ⚠️ windsor-dataブランチは毎回作り直される

`windsor-data.yml` は毎回 `git init` + `git push --force` でブランチを作り直す。
**前回の `clarity_7d.json` を読み込んでマージしないと、毎日1日分に戻る。**

そのためワークフローに「前回のclarity_7d.jsonを取り出す」ステップを置き、
`origin/windsor-data` から `prev/clarity_7d.json` へ取り出してからスクリプトへ渡している。
マージ・剪定は `scripts/lib/clarity-merge.mjs` の純粋関数で行い、
`scripts/test/clarity-merge.test.mjs`（13ケース）がワークフロー内で毎回走る。

| ルール | 内容 |
|---|---|
| 重複排除 | 同じ `date` は**新しい方で置き換え**（同日再実行を想定） |
| 剪定 | `today` から**8日以上前**は落とす。7日前は残す |
| 異常値 | 未来日付・壊れた日付の行は残さない（鮮度判定を誤らせるため） |
| 取得失敗 | **前回分を消さない**。当日分だけ `no_data: true` で積む |

### レート制限の守り方

Clarityは**1プロジェクトあたり10リクエスト/日**。日次実行なので、
**1実行あたり最大3リクエスト**に固定してある（本番2＋リトライ1）。

- 1回目：全体サマリー
- 2回目：`dimension1=URL` × `dimension2=Device`（どのページ・どの端末で詰まっているか）
- リトライは1回だけ。**401/403/404は再試行しない**（何度投げても同じで、回数を無駄にするだけ）

### 失敗しても止めない

取得に失敗してもスクリプトは異常終了しない。失敗させると、
**同じジョブで取得済みの広告データまでコミットされなくなる**ため。
失敗は `_summary.json` の `results.clarity_7d` と実行ログに残す。

```
"clarity_7d": { "ok": false, "error": "...", "fetched_at": "...",
                "days": 3, "no_data": false, "latest_data_date": "2026-08-19",
                "requests_used": 2 }
```

### 週次経営レビューでの使い方

Routine「週次経営レビュー」は既に
`git show origin/windsor-data:clarity_7d.json` を読む指示を持っており、
**存在すれば改善提案の根拠として引用し、無ければスキップする**設計になっている。
今回の実装でこのファイルが実際に置かれるようになったため、
次回の月曜レビューから行動データが根拠として載る。

`no_data: true` のときは「Clarityにまだデータがありません」と書き、数字を作らないこと。

## 6. Metaピクセルの状態

`src/components/MetaPixel.astro` は環境変数 `PUBLIC_META_PIXEL_ID` が設定されているときだけ
出力される設計。**このセッションからは本番サイトへの到達が遮断されていて、
実際にピクセルが出ているかを確認できていない。**

オーナー確認事項：
- [ ] Vercel → プロジェクト → Settings → Environment Variables に
      `PUBLIC_META_PIXEL_ID` が本番環境向けに設定されているか
- [ ] Metaイベントマネージャで PageView / Schedule / Lead / Contact が届いているか
      （2026-08-19以降、予約クリック・電話タップでも **Lead** が届くようになっている）

### イベント設計（2026-08-19〜）

| CTA | 送るイベント |
|---|---|
| HPB予約・クーポン | `Schedule` ＋ `Lead` |
| LINE | `Lead` |
| 電話（tel:） | `Contact` ＋ `Lead` |

HPBは外部ドメインでサンクスページにピクセルを置けないため、サイト側で取れる
最も購入に近いシグナルが「予約クリック」になる。これをSchedule だけに入れると
Leadが LINE 分（28日で21件）しか溜まらず、キャンペーン目的をトラフィックから
**リード最適化**へ引き上げられない。両方送ることで、Schedule/Contact の内訳を
保ったまま Lead を集約できる（`content_name` で内訳を判別可能）。
GA4の実測（28日：予約273＋LINE21＋電話21＝315件）から、**Leadは週70件前後**になる見込み。

- 週50件を安定して超えたら、Meta広告のキャンペーン目的を **リード獲得** に変更する
- さらに回数券の成約実績は施策A（`docs/capi-offline-events.md`）でCAPI経由で送る
