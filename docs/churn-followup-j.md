# 施策J：離脱予兆リスト — 実現可否の整理（未実装）

提案書の施策J「kpi-scraperのデータから『回数券残あり×最終来店30日超』を週次で自動抽出し、
週次経営レビューに『今週フォローすべき5人』として掲載」について、**現状では実装できない**。
理由と、実装するための選択肢をまとめる。オーナーの判断待ち。

---

## なぜ今は作れないのか

施策A（Meta CAPI）とまったく同じブロッカーで止まっている。

**kpi-scraperは顧客単位のデータを一切持っていない。**

`kpi-data` ブランチの `weekly_kpi.json` にあるのは週次の集計値だけ：

```json
"metrics": { "sales_total": 790920, "total_visits": 24, "new_visits": 17,
             "new_ticket_sales": 8, "renewal_ticket_sales": 1, ... }
```

「誰が」「いつ最後に来たか」「回数券が何回残っているか」という行は存在しない。
これは事故ではなく設計で、`kpi-scraper/fetch.mjs` は
「顧客名などのセル値・生HTMLは一切保存しない」方針で書かれており、
探索モードでも顧客管理・来店記録・問い合わせ一覧のページを**意図的に開かない**
（`kpi-scraper/fetch.mjs:260` 付近）。

さらに、`kpi-data` ブランチは週次ジョブが毎回 `git init` + `git push --force` で
作り直すため、前週との差分（＝「最終来店から◯日」の判定に必要な履歴）も残らない。

## 選択肢

### 案1：電話マスタ経路に相乗りする（推奨）

施策Aで採用した「Cowork月次タスクがサロンボードのスクショから抽出して
Driveの `phone-master_YYYY-MM.json` に入れる」経路に、フィールドを2つ足すだけ。

```json
{
  "name": "山田太郎",
  "phone_hash": "...",
  "purchases": [{ "date": "2026-08-12", "value": 132000 }],
  "last_visit": "2026-07-05",      ← 追加
  "ticket_remaining": 6            ← 追加
}
```

- ✅ 新しいデータ経路を作らなくてよい（施策Aの契約を1つ増やすだけ）
- ✅ サロンボードへのプログラムアクセスは発生しない（規約遵守）
- ✅ 店舗システムのスクレイピング範囲を広げずに済む＝現在のプライバシー設計を維持できる
- ⚠️ **鮮度が月次**。「最終来店30日超」の判定が最大1ヶ月ずれる
  → 実運用上は「30日超」を「45日超」にするなどの調整で吸収できる
- ⚠️ Cowork側（別システム）の改修が必要

### 案2：店舗システムの顧客管理ページを取得する

`system.zn-stretch.com` の顧客管理画面をPlaywrightで開いて顧客単位データを取る。

- ✅ 週次で鮮度が高い
- ✅ サロンボードではなく自社の店舗システムなので規約違反ではない
- ❌ **現在の「顧客情報ページは開かない」設計を覆すことになる**（オーナー判断が必要）
- ❌ そもそも該当画面が存在するか未確認。discoveryモードでの調査から必要
- ❌ 氏名を扱うことになるため、出力先・保存方法の設計をやり直す必要がある

### 案3：店舗システムのCSVエクスポート（あれば）

顧客一覧をCSVで出せるなら、月1回手動でDriveへ置く。案1と同じ扱いになる。

## どちらの案でも決めておくべきこと：氏名をどこに出すか

店長が電話をかけるには**氏名が必要**。しかし現在の方針では、氏名を
リポジトリにもログにも残さないことにしている（施策Aのレポートも件数のみ）。

出力先の候補：

| 出力先 | 氏名が残る場所 | 評価 |
|---|---|---|
| Google Drive のスプレッドシート | Drive（既にサロンボードのスクショがある場所） | ◎ 既存の保管場所と同じ粒度で一貫する |
| GitHub Actions の実行サマリー | Actionsのログ（保持期間90日） | △ リポジトリ外だがGitHubに残る |
| capi-state / kpi-data ブランチ | Gitの履歴に永久に残る | ✕ 採用しない |
| 週次レビューのチャットに直接出す | チャット履歴 | ○ 都度限りで残りにくい |

**推奨：Google Drive のスプレッドシートに書き出す。** サロンボードの顧客スクショが
すでに置かれている場所なので、個人情報の保管場所を増やさずに済む。

## 実装したときの姿（決まり次第すぐ書ける）

```
scripts/churn-followup.mjs
  1. Driveから phone-master_*.json を取得（施策Aの capi-upload.mjs と同じ認証・同じ関数）
  2. ticket_remaining > 0 かつ last_visit が N日以上前 のレコードを抽出
  3. 最終来店が古い順に上位5名を選ぶ
  4. Driveの「フォローリスト」スプレッドシートへ書き出す（氏名・最終来店日・残回数）
  5. 件数だけをActionsのサマリーに出す（氏名は出さない）

.github/workflows/churn-followup.yml
  - schedule: 毎週月曜 8:00 JST（週次経営レビューの1.5時間前）
```

施策Aで作った `scripts/capi-upload.mjs` のDrive取得部分（サービスアカウントのJWT認証、
`files.list` / `files.get`）がそのまま再利用できるため、実装は半日かからない。

## 2026-08-20 オーナー判断：案2（店舗システムから取得）で進める

施策A側の運用検討の中で、次が判明・決定した。

- **店舗システムには顧客IDが自動採番されている**（オーナー確認）。氏名照合より遥かに堅牢な
  キーが使えるため、案2の価値が当初想定より高い
- サロンボードの売上CSVには顧客IDの列が無く（`お客様番号` は全行空欄）、氏名でしか
  照合できない。実際に**同姓同名がすでに1件存在**していた
- したがって **案2（店舗システムから顧客単位データを取得）を採用**し、
  顧客情報ページを開く設計変更を承認した

まず `.github/workflows/customer-discovery.yml`（手動実行）で、
店舗システムの顧客画面に「顧客ID・電話番号・回数券残・最終来店日」があるかを調査する。
調査レポートは**列の見出しと値の種類だけ**を出し、氏名・電話番号・セルの値は一切含まない
（`kpi-scraper/lib/page-structure.mjs` がブラウザ内で値を種類ラベルに潰す）。

調査結果しだいで、施策Aの電話番号取得と施策Jの離脱予兆リストが**同じ経路で同時に解ける**。
