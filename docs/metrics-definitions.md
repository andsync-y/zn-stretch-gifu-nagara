# 指標定義書（数字を結論に使う前に必ず読む）

2026-08-22 作成。**この対話で5件の誤りを出した反省から作った。**
原因はすべて同じ「その数字が何を数えているかを確認せずに結論に使った」。

## 鉄則

1. **新しいフィールドを使う前に `get_fields` で定義を読む。** 名前から推測しない
2. **単位の違う数字を比較しない。** 特に「アクション数」と「実来店数」
3. **1つの指標だけで判断しない。** CPAを見るならCPCも見る（8/14の失敗はこれ）
4. **店舗システムの指標は定義をオーナーに確認する。** 「離客」で誤読した

|---|---|---|

**過去の誤り**：`clicks` から「Meta CPC ¥32」と算出したが、実態は

## 広告：コンバージョン系の落とし穴

| フィールド | 実際に数えているもの |
|---|---|
| google_ads `conversions` | **入札が最適化している対象**。実来店ではない |
| GA4 `click_reserve` / `click_line` / `click_tel` | **サイト全体**のCTAクリック（全流入） |
| facebook `actions_..._pixel_lead` | **Meta広告経由のみ**のLead |

**GA4のCTAクリックとMetaのLeadは別物。** GA4はオーガニック・Google広告・
直接流入を全部含む。Metaの学習に使えるのは広告帰属分だけ。

**過去の誤り**：GA4の週104〜118件を「MetaのLeadが週100件超」と誤認。
実際のMeta帰属Leadは週6.3件だった（2026-08-22）。

## 店舗システムの指標

| 指標 | 定義（オーナー確認済み） |
|---|---|
| **離客** | **新規来店数 − 回数券販売(新規)本数。それだけ。**（2026-08-24に6週分すべてで一致を確認） |
| 新規離客率 | 離客の裏返しなので、**新規販売率とほぼ同じことを言っている**。単独で深刻度を判断しない |
| 新規販売率 | 回数券販売(新規)本数 ÷ 新規来店数 |
| 更新販売率 | 更新販売本数 ÷ 使い切り人数。**回数券の消化に数ヶ月かかるため、開店初期の数値は評価不能** |
| 稼働率 | 稼働(H) ÷ 営業(H)。営業(H)＝ベッド4台×営業時間 |

⚠️ **「次回予約も取らなかった人」という説明は、データと合わない**（2026-08-24 検証）。
次回予約率は26〜40%あるのに、離客数からは1人も引かれていない。6週すべてで
`離客 = 新規 − 回数券販売` がぴったり一致する。つまり**離客率は新規販売率の裏返しにすぎず、
次回予約を取った人も「離客」に数えられている。** 実態より悲観的に出るので、
単独で深刻度を語らないこと。**次回予約率と必ず並べて見る。**

例：8/17週は離客率94.7%だが、同じ週の次回予約率は40.0%（過去最高）だった。

**過去の誤り**：離客率74.1%を「新規の4分の3が消える」と解釈したが、
実際は新規販売率26%の裏返しで、KPI目標を達成していた（2026-08-22）。

## 来店経路（店舗システム）— 唯一の「広告→実来店」の接点

`by_channel`（来店経路別販売状況）に、**新規1人ずつがどの経路から来たか**が入っている。
2026-08-24まで一度も取得していなかった。**広告の良し悪しを最終的に判定できるのはここだけ。**

⚠️ 3つの注意：

1. **受付での自己申告**。厳密な計測ではない
2. **「未記入」は再来店の人**（2026-08-24 オーナー確認）。経路を聞くのは初回だけなので空欄になる。
   ダッシュボードの「新規」には含まれるが、**新規獲得ではないので、経路分析からは必ず除く**。
   2026年8月は63人中11人（17%）が未記入＝再来店。**除かずに数えると獲得の落ち込みが隠れる**
   （7月6人→8月14.8人と増えているため、除外前は−29%、除外後は−38%になる）
3. **Google広告→/lp→HPBで予約、という人は「ホットペッパービューティー」に記録される。**
   検索広告の成果がHPBに吸収されるため、この表だけで「Google広告は効いていない」と結論しない

## 稼働率の分母

| | 値 |
|---|---|
| 店舗システムの計算 | ベッド4台 × 日数 × 12h ＝ **月1,488h**（31日）。8月の稼働201h → 13.5% |
| `zenryoku-facts` の旧記述 | 月400時間 |

**3.7倍ずれている。** 2026-08-24の週次レビューは400h基準で「稼働率57%」と報告したが、
同じ月を店舗システムは13.5%としている。**稼働率を語るときは、どちらの分母かを必ず書く。**

## データの到着遅延（判断の期日をこれで決める）

| 媒体 | 遅延 | 例 |
|---|---|---|
| **Google広告** | **2日** | 8/24朝に取れるのは 8/22 まで。`google_ads_yesterday` も8/22を返す |
| Meta広告 | 1日 | 8/24朝に 8/23 まで取れる |
| GA4 | 1日 | |
| Clarity | 当日（3日ぶんの集計） | |

**2026-08-24に確認。** リレーの時刻を早めても、手動で再取得しても変わらない。Windsor側かGoogle側の
処理遅延であり、こちらでは短縮できない。

⚠️ **「変更した翌朝に効果を見る」はGoogleでは成立しない。**
変更日をD日とすると、D日のフル1日ぶんのデータが見えるのは **D+2日の朝**。
検証日を設定するときは必ず2日足すこと。

## Clarity の読み方の注意

| 指標 | 注意 |
|---|---|
| `averageScrollDepth` | **ページの全長に対する割合。** 長いページほど低く出る。ページ間の比較に使わない |
| `EngagementTime.activeTime` | ページ長に依存しない。**熱量の比較はこちらを使う** |
| `pagesPerSessionPercentage` | LPのような単独完結ページでは1.0付近が設計通り。直帰の悪さとして読まない |
| `Browser` | InstagramApp / FacebookApp が多い＝Metaのアプリ内ブラウザ。計測がやや不安定 |

## Meta フリークエンシー（広告疲労）

`frequency` = 1人あたりの平均表示回数。**週3〜5回を超えたらクリエイティブの入れ替えを検討する。**

⚠️ **日次の `frequency` や `reach` を足し算しない。** 同じ人が複数日に見た分が重複するため、
日次を合算すると実態より低く出る。期間の値が要るときは、`date` を外して期間指定で問い合わせる。

**2026-08-10〜08-23の実測**：日次は1.05〜1.21だが、14日の実値は A=1.79 / B=2.51。基準内。

## Google 表示シェアの内訳（打ち手が正反対になる）

| フィールド | 意味 | 高いときの打ち手 |
|---|---|---|
| `search_impression_share` | 出られたはずの検索のうち実際に出た割合 | — |
| `search_budget_lost_impression_share` | **予算不足**で出られなかった割合 | 増額が効く |
| `search_rank_lost_impression_share` | **広告ランク不足**で出られなかった割合 | **増額しても消化できない。** 品質スコア・入札額・LPの見直し |

**2026-08の実測**：8/18〜8/20は予算不足0%・順位不足68〜76%。この状態で増額しても1円も使えない。
8/16に/lp切替＋新RSAへ差し替えており、新しい広告は品質スコアの履歴が無いため広告ランクが下がる。時期が一致する。

`period-compare.mjs` に検知を実装済み（`GOOGLE_LOSING_TO_RANK_NOT_BUDGET`）。

## 予約通知メール由来の数字（`scripts/booking-count.mjs`）

**メールの通数を予約件数として数えてはいけない。** 2026-08-31 に同じ日のうちに3回間違えた。

| 落とし穴 | 正しい扱い |
|---|---|
| 件名で `予約連絡` を検索する | **「【当日◯時】直前予約が入りました」が落ちる。** 件名で絞らず `from:salonboard.com` で引く |
| キャンセル→取り直しを2件と数える | 同一人物・同一来店日の再予約は**取り直し1件**。時刻だけ変える形が実在する |
| 同じ予約番号の通知を重ねて数える | 予約番号で重複排除する |
| 月曜を土日と比べる | 曜日差が3〜5倍ある（8月実測：土19・日14・木4）。**同じ曜日と比べる** |

⚠️ **電話予約（予約番号 `YH…`）はメールが飛ばないため、1件も見えない。**
2026-08-24 の来店5件のうち2件が電話予約だった。この経路で出せるのは
**「ネット予約（`BF`）の実数」であって「予約の実数」ではない**。総数は店舗システムで確認する。

⚠️ **1日あたり数件の母数では、変化を数日では検知できない。**
初回予約は月80件＝日2.6件。50%落ちても気づくのに約2週間かかる。
「変更して数日様子を見る」は安全弁として機能しない。効果を確かめたい変更は、
件数ではなく**動作そのもの（実機で通るか）**で確認する。

### 経路アンケートの回答の在り処

⚠️ **`■ご要望・ご相談` ではない。** 2026-08-31 に「そこに載るはず」と想定して実装したが、
実際の1通目（BF60199476・15:21受付）で否定された。`■ご要望・ご相談` は `-` のままで、
回答は **`■サロンからお客様への質問` ブロック末尾の「回答：」行**に入る。

```
■サロンからお客様への質問
　質問：…当店を「最初に」知ったきっかけの番号を下記にご記入ください。
【1】ホットペッパーで検索 …
　回答： 【1】
```

`booking-count.mjs` は `surveyAnswer`（生）と `surveyChannel`（1〜6）として取り出し、
日別に経路の内訳を出す。番号以外の自由記述は `surveyChannel` に落とさない。

### 経路アンケートを読むときの2つの制約

**① 既存客の回答を分母に入れない。**
初回の1通目（BF60199476）は**回数券保有者がHPBから予約したもの**だった。
既存客の「最初に知ったきっかけ」は何年も前の出来事で、今回の来店経路ではない。
`booking-count.mjs` は初回限定クーポンの予約だけを経路の分母にし、
回数券・チケット消化の予約は `surveyFromNonFirst` として分けて出す。

| 分類 | 判定 |
|---|---|
| `first` | 初回限定クーポンを使っている |
| `repeat` | メニューが回数券・チケット消化 |
| `unknown` | どちらとも言えない（通常メニューをクーポンなしで予約した等） |

**② 【1】は他経路を吸収する。**
設問は「**最初に**知ったきっかけ」だが、それでも防ぎきれていない。
オーナー観測では **公式LINE →「予約方法」バナー → ネット予約 → HPBへ遷移** という経路が実在し、
この人はHPB上で予約するので【1】ホットペッパーで検索を選びやすい。看板・通りがかりも同様。

**したがって【1】の件数は上限値であり、「HPB経由が多い」と読んではいけない。**
広告の効果として意味があるのは **【2】Instagram・Facebookの広告 と【3】Google検索・広告 の増減**。
LINE経由を分けたければ、アンケートではなく**LINEのバナー先に別クーポンを割り当てる**のが確実
（予約通知メールの「ご利用クーポン」で判別できる）。
