# Meta広告 CAPIオフラインイベント送信

回数券の成約実績を、Meta広告に**オフラインコンバージョン**として送る仕組み。
狙いは配信最適化を「体験に来る客」ではなく「**回数券を買う客**」に寄せること。

- スクリプト: `scripts/capi-upload.mjs`（依存パッケージなし・Node 22の標準機能のみ）
- ワークフロー: `.github/workflows/capi-upload.yml`（**毎週月・木 10:00 JST** ＋ 手動実行）
- 状態の保存先: **`capi-state` ブランチ**（`capi-sent.json` と `capi-report_YYYY-MM.md`）

> `kpi-data` ブランチは週次ジョブ（`kpi-data.yml`）が毎回 `git init` + `git push --force` で
> 作り直すため、送信済み管理を置くと毎週消えて二重送信になる。そのため専用の `capi-state`
> ブランチを使い、こちらは履歴を保持したまま積み上げる。

## パイプライン全体像

**成約の把握は自動**、オーナーの手作業は「**まだ電話番号を登録していない顧客の分だけ**」に限られる。

| # | 頻度 | 誰が | 内容 |
|---|---|---|---|
| 1 | 毎週月・木 10:00・自動 | このリポジトリ | 店舗システムの「来店記録」からCSVをダウンロードし、`回数券購入` が入っている行だけを抽出（顧客ID・成約日・金額） |
| 2 | 同ジョブ内・自動 | このリポジトリ | Driveの**電話帳** `phone-book.json`（顧客ID → 電話ハッシュ）と突合し、**7日以内**の分をMeta CAPIへPurchase送信 |
| 3 | 同ジョブ内・自動 | このリポジトリ | 突合できなかった顧客IDを**実行サマリーに一覧表示** |
| 4 | ③が出たときだけ・手動 | オーナー | その顧客IDを店舗システムで開いて氏名を確認 → サロンボードの顧客情報から電話番号をスクショ → Drive「31_顧客電話_取込」へ |
| 5 | 毎月2日 9:00・自動 | Cowork定期タスク | スクショをOCR → 電話番号を正規化・SHA256ハッシュ化 → 電話帳 `phone-book.json` へ**追記** |

④は**1顧客につき生涯1回**でよい。顧客IDは店舗システムが自動採番するので、
一度登録すればその顧客の以後の回数券購入はすべて自動で送信される。

サロンボード（salonboard.com）へのプログラムからのアクセスは規約で禁止されているため、
**このリポジトリからは一切行わない**。④のスクショ取り込みが唯一の接点。

### なぜ来店記録CSVを使うのか（2026-08-20 実物で確認）

| | サロンボードの売上CSV | 店舗システムの来店記録CSV |
|---|---|---|
| 取得 | 手動でダウンロード → Driveへ | **スクリプトが自動でダウンロード** |
| 顧客の識別 | 顧客名（表記ゆれあり） | **顧客ID（自動採番・一意）** |
| 指名回数券の混入 | `カテゴリ` 文字列で除外が必要 | **`回数券購入` と `指名チケット` が別列**なので構造的に起きない |
| 電話番号 | あり（＝スクショ元） | **なし**（DOM全体を探しても存在しない） |

来店記録CSVは19列（UTF-8）:
`来店日 / 顧客名 / 顧客ID / 性別 / 年代 / 担当 / 来店種別 / 来店経路 / 指名 / コース / 延長 /
次回予約 / 回数券購入 / 指名チケット / 備考 / 施術売上 / 回数券売上 / 指名売上 / 合計売上`

`回数券購入` には `5回券(90分)` のような商品名が入り、金額は `回数券売上` 列に入る。
`指名チケット` / `指名売上` は別列なので、**指名料のチケットは金額にも混ざらない**。

抽出条件は「`回数券購入` が空でない」だけ。判定に文字列マッチを使わないので、
商品名が増えても取りこぼさない。

### 紹介経由をどう除くか（2026-08-20 オーナー判断）

紹介客を広告の学習信号に混ぜると、Metaが「広告と関係なく来る人」を学習してしまい、狙いと
逆方向に最適化される。そこで次の2つを除く。

1. **来店経路に「紹介」を含む顧客**（`ご紹介` `友人紹介` などの表記ゆれも部分一致で拾う）
2. **2026-06-19以前の成約**（この日までの来店はすべて紹介によるもの）

判定は**顧客単位**で行う。`来店経路` は再来店の行では埋まっていないことがあり
（実測で `—` が14行）、成約した行だけを見ると紹介客を取りこぼすため、
取得したCSV全体のどれか1行でも「紹介」だった顧客IDを集めてから、その顧客の成約を除く。

`来店経路` 列が見つからない場合は、黙って除外をやめずに**ジョブを失敗させる**。

実測（2026-08-20・直近70日）:

| | 件数 |
|---|---:|
| 回数券の成約（除外前） | 58件 |
| − 紹介客の成約 | 8件 |
| − 2026-06-19以前の成約 | 9件 |
| **送信対象** | **41件 / 38人 / 2,219,360円** |

回数券を買った行の来店経路の内訳（重複含む）:
ホットペッパービューティー26 / 紹介21 / `—`14 / インスタ広告（60分）8 / インスタ広告（90分）8 /
看板6 / インスタ広告（動画）6 / Googleマップ4 / インスタ広告3 / HP2 / Facebook1

> `—`（経路が記録されていない行）は紹介とは扱わず残している。
> その顧客の別の行に「紹介」があれば、顧客単位の判定で除かれる。

#### 「この紹介客は入れたい」場合（オプトイン）

紹介客でも、**電話帳 `phone-book.json` に登録すれば送信対象になる**。
電話帳への登録はオーナーが手作業でやることなので、載っている＝意図して入れた人、とみなす。

そのため抽出側では紹介・広告開始前の成約を**捨てずに `ad_signal: false` の印を付けるだけ**にし、
送信側が次のように判断する。

| 印 | 電話帳 | 結果 |
|---|---|---|
| なし（広告経由） | あり | **送る** |
| なし（広告経由） | なし | 送らない。**「電話番号の登録が必要」の一覧に出す** |
| `ad_signal: false` | あり | **送る**（オーナーが意図して入れた人） |
| `ad_signal: false` | なし | 送らない。一覧にも出さない（紹介客を集めさせないため） |

実行サマリーに「紹介・広告開始前だが電話帳にあるので送った成約」の件数を毎回出すので、
意図せず紹介客が混ざり始めたら気づける。

### 期間の取り方（2026-08-20 実機で確定）

来店記録CSVには**件数の上限があり、超えると古い行から落ちる**。
画面で「今年」（2026-01-01〜08-20）を選んでも、CSVは **347行・2026-06-16以降しか返らなかった**。

さらに、期間の入力欄（`#vfFromInput` / `#vfToInput`）にスクリプトから値を入れる方式は使えない。
値を入れると**画面の期間表示は変わるのに、CSVの中身は変わらなかった**（指定していない期間の
データが返る）。静かに間違った数字が出るため、この方式は実装から外してある。

そこで、**実際に押せるプリセットボタンだけ**を使う。

| プリセット | 役割 | 実測（2026-08-20） |
|---|---|---|
| 先月 | 必ず取る | 2026-07-01〜07-31 / 来店156行 → 回数券 **24件** |
| 今月 | 必ず取る | 2026-08-01〜08-20 / 来店87行 → 回数券 **17件** |
| 今年 | 取れた分だけ上積み | 上限で 2026-06-16 以降のみ（347行） |

「先月」＋「今月」で**先月1日〜今日**を必ず覆う。毎月動かせば前回の実行範囲と必ず重なるので、
取りこぼしは起きない。1回あたり150行前後なので上限にも当たらない。

検証は**画面の表示ではなくCSVの中身**で行う。必ず覆うべき期間が欠けていたら
**ジョブを失敗させる**（件数が少ないまま送ると、Metaに「成約が減った」と誤って学習させてしまうため）。

> 月次実行を数ヶ月飛ばすと、「先月＋今月」では届かない過去の成約は取り戻せない
> （「今年」で拾える約2ヶ月ぶんが上限）。ジョブが失敗したら放置せず、その月のうちに直すこと。

### phone-book.json のフォーマット（Cowork側の出力先）

Driveフォルダ「32_顧客電話_マスタ」に置く。**月ごとに作り直さず、1ファイルに追記していく**
（顧客IDと電話番号の対応は変わらないため）。

```json
{
  "records": [
    { "customer_id": "10000001", "phone_hash": "3a7bd3e2360a3d29eea436fcfb7e44c735d117c42d1c1835420b6b9942dd4f1b" }
  ]
}
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `customer_id` | ✅ | 店舗システムの顧客ID（文字列。桁数は仮定していない） |
| `phone_hash` | ✅ | `81`から始まる正規化番号のSHA256（小文字16進64桁）。これ以外はスキップ |

補足:
- 配列そのまま `[{...}]` でも読める。`phone-book_2026-08.json` のように分割されていても全部読む。
- 同じ `customer_id` が複数あれば、**後に読んだ方**（ファイル名順で後ろ）が勝つ。
- 氏名を入れても構わないが、このスクリプトは**読まない・出力しない**。

### phone-master_YYYY-MM.json のフォーマット（旧経路・後方互換）

来店記録から成約を取れるようになったため、この経路は**もう必須ではない**。
既存ファイルを無駄にしないよう読み込みは残してある。

```json
[
  {
    "name": "山田太郎",
    "name_kana": "ヤマダタロウ",
    "phone_hash": "3a7bd3e2360a3d29eea436fcfb7e44c735d117c42d1c1835420b6b9942dd4f1b",
    "purchases": [
      { "date": "2026-08-12", "value": 132000, "content_name": "回数券" }
    ],
    "source_file": "customer_2026-08.png",
    "extracted_at": "2026-08-02T00:12:00Z"
  }
]
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `phone_hash` | ✅ | `81`から始まる正規化番号のSHA256（小文字16進64桁）。これ以外はスキップ |
| `purchases[].date` | ✅ | 成約日。`YYYY-MM-DD` / `YYYY/M/D` / `YYYY年M月D日` を受け付ける |
| `purchases[].value` | ✅ | 成約金額（円）。`132000` / `"¥132,000"` / `"132000円"` を受け付ける。**Purchaseイベントは金額必須**のため、無い成約は送信されない |
| `purchases[].content_name` | – | 省略時は `回数券` |
| `name` / `name_kana` | – | 突合に使わなくなったので任意。**送信もレポート出力もしない** |

補足:
- `purchases` が無いレコードは「成約情報なし」として黙ってスキップされる（エラーにしない）。
- 単発形の `purchase_date` / `purchase_value` も後方互換で受け付ける。
- 同じ成約が複数月のマスタに載っていても、`(日付, 金額, 商品名)` が同じなら1件に畳まれる。
- 配列の代わりに `{"records": [...]}` でも読める。

## 送信されるイベント

```json
{
  "event_name": "Purchase",
  "event_time": 1786503600,
  "action_source": "physical_store",
  "event_id": "20260812_696c6457de7897b0",
  "user_data": { "ph": ["<sha256ハッシュ>"] },
  "custom_data": { "currency": "JPY", "value": 132000, "content_name": "回数券" }
}
```

- 送信先: `POST https://graph.facebook.com/v26.0/{META_DATASET_ID}/events`
  （v26.0は2026-07-29リリースの最新版。`META_GRAPH_VERSION` で差し替え可能）
- `event_time` は成約日の**JST正午**。日付しか分からないため、どのタイムゾーンで
  解釈しても同じ日になる時刻を採っている。
- `event_id` = `{成約日YYYYMMDD}_{phone_hash先頭16文字}`。Meta側の重複排除キーであり、
  こちらの送信済み管理キーでもある。
- 同一顧客・同一日に複数の成約があると `event_id` が衝突するため、**金額を合算して1件**に
  まとめる（レポートに件数を出す）。

### ⚠️ 送信できるのは7日以内の成約だけ（2026-08-20 実測）

各所の資料には「オフラインイベントは62日以内」とあるが、**このデータセットでは通らなかった**。

| 試したこと | 結果 |
|---|---|
| 62日窓・`upload_tag` なし | ✕ **バッチ全件拒否** |
| 62日窓・`upload_tag` あり | ✕ 同じく全件拒否 |
| **7日窓** | **○ `events_received: 2`・エラーなし** |

拒否時のエラー:

```
HTTP 400 / code 100 / error_subcode 2804003
「イベントタイムスタンプが古すぎます」
「イベントは、7日以内のイベント発生時点で送信される必要があります」
```

Metaは**1件でも古いイベントがあるとリクエスト全体を拒否**する（部分的にも通らない）。
オフラインイベントセット廃止（2025-05）後は、データセットに統合された結果
7日窓に揃えられたものと思われる。

そのため **`CAPI_MAX_AGE_DAYS` の既定を7**にし、**実行を週2回（月・木）**にしてある。
7日窓に対して3〜4日間隔なので、1回失敗しても次の回で拾える。
`capi-sent.json` で送信済みを管理しているので、重なって送っても二重送信にならない。

> **未確認**: 「過去のコンバージョンのアップロード」を許可する設定がイベントマネージャの
> どこかに存在するかは確認できていない（オーナーが探した範囲では見つからず、
> Metaの公式ドキュメントはこの実行環境から参照できない）。
> もし見つかって有効にできれば、`max_age_days` を62に戻して過去分も送れる。

#### 7日窓で送れない過去分の活かし方

初回時点で6/21〜8/13の成約（約40件）は送れない。捨てずに使うなら、
Metaの**カスタムオーディエンス（顧客リスト）**に購入者の電話番号をアップロードし、
そこから**類似オーディエンス**を作る。Purchase最適化の学習には使えないが、
「回数券を買う人に似た人」への配信には使える。
※類似オーディエンスの作成には人数の下限があるため、41人で足りるかは実際に試して確認する。

### 除外されるもの

| 条件 | 理由 |
|---|---|
| `指名チケット` のみの行 | 指名料のチケットであって施術の回数券ではない（`回数券購入` 列が空なので構造的に除外される） |
| **紹介経由の顧客** | 広告経由ではない。送るとMetaが広告と関係のない層を学習してしまう（電話帳に登録されていれば送る） |
| **2026-06-19以前の成約** | この日までの来店はすべて紹介によるもの（同上・電話帳にあれば送る） |
| 電話帳に顧客IDが無い | 突合できない。件数と顧客IDを実行サマリーに出して、登録を促す |
| 成約から7日より前 | 実測でMetaが拒否する（`max_age_days` で変更可・上の⚠️参照） |
| 未来日付 | OCRの読み取り誤りの可能性が高い |
| 金額がない | Purchaseイベントは `value` + `currency` が必須 |
| `capi-sent.json` に既にある | 二重送信の防止 |
| `phone_hash` が64桁16進でない | 生番号の混入・OCR崩れを弾く |

## 個人情報の扱い

- 生の電話番号・メールアドレスは**リポジトリ・ログ・レポートのどこにも書かない**。
  このスクリプトが受け取るのは最初からSHA256ハッシュ済みの値だけ。
- 来店記録CSVには顧客名が入るが、**Actionsの実行環境（毎回破棄）の中だけ**で処理する。
  リポジトリにもDriveにも保存せず、抽出結果のJSONにも顧客名を入れない
  （`kpi-scraper/lib/visit-csv.mjs` が氏名列を読まない。テストで検証している）。
- 中間ファイル `out/ticket-purchases.json` は顧客IDを含むため、ジョブ末尾で必ず削除し、
  アーティファクトにも上げない。`.gitignore` でもコミットを防いでいる。
- 突合できなかった**顧客IDは実行ログ・実行サマリーにのみ**出す。
  `capi-state` ブランチに残る `capi-report_YYYY-MM.md` には件数だけを書き、IDは残さない。
- 氏名は突合に使わないため、**一切出力しない**（レポートは件数と理由のみ）。
- dry_runのpayloadサンプルでもハッシュ値は `<sha256 redacted>` に伏せる。
- `capi-sent.json` に残るのは `event_id`（日付＋ハッシュ先頭16文字）のみ。
  62日窓を大きく超えた400日より古いものは自動で削除する。

## 運用手順

### 初回は3段階で確認する

1. **dry_run**（Actions → 「Meta CAPIオフラインイベント送信（月次）」→ Run workflow、
   `dry_run` は既定の **true** のまま）
   → 送信せず、件数とpayload概要だけログに出る。件数・金額が妥当か確認する。
2. **テスト送信**（`dry_run` を **false**、`test_event_code` にイベントマネージャの
   「テストイベント」タブに表示されるコードを入れる）
   → Metaのテストイベントタブに届くか確認する。この送信では `capi-sent.json` を更新しないので、
   同じ成約を本送信で送り直せる。
3. **本送信**（`dry_run` を **false**、`test_event_code` は空）
   → 以降は毎月3日に自動で走る。

イベントマネージャへの反映確認は、送信から最大数時間かかることがある。

### エラー時

Drive取得失敗・Meta API 4xx などが起きた場合、ワークフローは**失敗**し、
原因（HTTPステータスとレスポンス本文）がログに出る。数字を作らず、送信済み管理も更新しない。

### 必要なSecrets

Settings → Secrets and variables → Actions

| 名前 | 内容 |
|---|---|
| `GDRIVE_SA_KEY` | GCPサービスアカウントのキーJSON（**中身をそのまま貼る**） |
| `META_DATASET_ID` | Metaイベントマネージャのデータセット（旧オフラインイベントセット）ID |
| `META_CAPI_ACCESS_TOKEN` | Conversions APIのアクセストークン |
| `ZN_SYSTEM_USER` / `ZN_SYSTEM_PASS` | 店舗システムのログイン情報（週次KPIジョブと共用・設定済み） |

## オーナー側の手動セットアップ・チェックリスト

> 画面の操作単位まで落とした手順は **[`docs/capi-setup-guide.md`](capi-setup-guide.md)** を参照。
> 所要40分。Metaはピクセルとデータセットが統合されたため、**既存のピクセルIDを
> そのまま `META_DATASET_ID` に使える**（データセットの新規作成は不要）。


- [ ] **Metaイベントマネージャ**（business.facebook.com/events_manager）でデータセットを作成
      → データセットIDを控える → Secretsの `META_DATASET_ID` へ
- [ ] 同じデータセットの「設定」→「Conversions APIのアクセストークンを生成」

## 参考：サロンボード売上CSVで見た回数券の内訳（2026-08-20）

> 現在の実装は**店舗システムの来店記録CSV**を使うため、以下の文字列による除外は不要になった。
> 「指名回数券を混ぜると何が起きるか」の記録として残す。

売上明細CSVを解析したところ、`区分=店販` に**2種類が混在**していた。

| カテゴリ | 2ヶ月の件数 | 金額帯 | 送信 |
|---|---:|---|---|
| 男性新規20%OFF！回数券 | 44 | 29,040〜132,000円 | ✅ |
| 男性紹介新規30%OFF！回数券 | 4 | 26,400〜57,750円 | ✅ |
| 女性回数券 | 1 | 34,650円 | ✅ |
| **指名回数券** | **25** | 9,900〜33,000円 | ❌ **除外**（オーナー判断 2026-08-20） |

「指名10回券」等は**指名料のチケット**であって施術の回数券ではない。送ると
Metaが「約1万円の買い物をする人」を学習してしまい、狙いと逆方向に最適化される。

実績：2026-06-21〜08-16 の2ヶ月で **49件 / 46人 / 2,591,710円**（月20〜24件）。
店舗システムの来店記録でも 2026-08-01〜08-20 の20日間で **17件 / 976,250円** と、同じ水準だった。
