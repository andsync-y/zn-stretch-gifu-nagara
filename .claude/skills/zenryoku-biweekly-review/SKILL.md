# 隔週レビュー（構造分析）

## なぜこれが要るのか

2026年8月、新規が7月比37%減った。原因は8/9のGoogle入札戦略変更によるCPC3倍化と、
安いMetaから高いGoogleへの予算移動だった。**日次監視も週次レポートも2週間気づかなかった。**

見逃した理由は3つ。このスキルはその3つを潰すためにある。

1. **日次は前日、週次は前週しか見ない。** 2〜3週かけて進む劣化は、どちらの視野にも入らない
2. **単一指標の閾値しか見ていない。** 「広告費が増えて訪問が減る」という*関係*の異常は検知できない
3. **「何を変えたか」と「そのあとどうなったか」を突き合わせる場所が無かった**

## 絶対に守ること

- **数字を結論に使う前に `docs/metrics-definitions.md` を読む。** 同じ月に指標の取り違えを5件出している
- **要因分解を手計算しない。** `scripts/period-compare.mjs` を使う
- **仮説を1つに決め打ちしない。** 候補を3つ以上挙げ、データで潰していく
- **分からないことは「未検証」と書く。** 推測を結論欄に混ぜない
- **売上を使う前に内訳と検算する。** `kpi-data` の `sales_total` は払い戻しを引いていない。
  施術＋回数券＋指名の合計と一致するか確かめ、内訳が無ければオーナーに1問だけ聞く。
  ここがずれると、週商→4週平均→月換算→分岐点までの距離まで全部ずれる（`zenryoku-data` の4章）

## 手順

### 1. 前回からの変更を洗い出す

`docs/ops-change-log.md` を読む。**ここが起点。** 指標を見る前に「何を触ったか」を先に把握する。

- 検証日が空欄、または検証日を過ぎて結果が空欄の行 → **今回の検証対象**
- 「未記入だった変更」の欄も確認する

### 2. 期間を決める

当期と前期で**日数を揃える**。直近2週間 vs その前の2週間が基本。

お盆・年末年始など営業日が欠けた期間が入る場合は、**その旨を明記した上で**比較する
（正規化しない。休業も実態の一部）。

### 3. データを集める

`zenryoku-data` スキルの手順に従う。優先順位は git経由 → Windsor MCP → windsor-action のmcpモード。

必要なもの:

| 項目 | 出典 |
|---|---|
| Meta 消化・**LPビュー**・**ピクセルLead** | `facebook_30d`（`clicks` は使わない） |
| Google 消化・クリック・CPC | `google_ads_30d` |
| 新規来店数（週次） | `kpi-data` ブランチ。足りなければ `kpi-data.yml` の `backfill_weeks` で遡る |
| GA4 予約アクション | `ga4_events_30d` |

30日を超える期間が要るときは Windsor の `get_data` を直接呼ぶ。

### 4. 機械的に比較する

入力JSONを作って実行する。**手で割り算しない。**

```bash
node scripts/period-compare.mjs --input <data.json>
```

入力の形はスクリプト冒頭のコメント参照。終了コード2は要対応の検知あり。

出力されるもの:
- 1日あたりの広告費・訪問・訪問単価・新規の期間比較
- **要因分解**（予算配分の変更 ／ 訪問単価の変化 のどちらで訪問を失ったか）
- **構造異常の検知**（費用と成果の逆行、単価の高騰、安い媒体から高い媒体への資金移動 など）

### 5. 検知結果を変更ログと突き合わせる

検知が出たら、**その時期に何を変えたか**を `ops-change-log.md` で探す。
時期が一致する変更があれば、それが第一容疑者。

一致する変更が無い場合は、外部要因を疑う（季節性・競合・媒体側のアルゴリズム変更・掲載順位）。
**この場合は「未特定」と正直に書く。**

### 6. 広告の外まで見る

訪問の減少幅より新規の減少幅が大きいときは、広告だけでは説明できていない。順に確認する。

- **営業日**：完全休業日はあったか（`docs/data/schedule-*.json` または当月のスケジュール）
- **シフト**：出勤トレーナー数、特に**土日と夜間**の人数
- **成約率**：新規販売率がKPI目標25%を維持しているか（落ちていれば接客側の問題）
- **HPB内の露出**：掲載順位・クーポン構成の変更。※サロンボードへのプログラムアクセスは規約で禁止。オーナーの手動確認に頼る

### 7. 報告する

**構成はこの順で固定する。** 結論を先に、限界を最後に。

1. **結論** — 3行以内。何が起きて、原因は何で、何をしたか
2. **数値の変化** — period-compare の出力を表で
3. **要因分解** — 寄与度を%で
4. **変更ログとの照合** — どの変更がいつの劣化に対応するか
5. **広告外の要因** — 営業日・シフト・成約率・HPB
6. **打ち手** — 実施済み／次にやる／保留、それぞれ期日つき
7. **この分析の限界** — 使えなかったデータ、未検証の項目を必ず書く

出力先は**Artifact**（`artifact-design` スキルを読んでから作る）。
リポジトリには `docs/` に分析メモを残し、`docs/AI_CHANGELOG.md` に追記する。

### 8. 変更ログを閉じる

検証した行の「結果」欄を埋める。次回の検証対象を減らすため。
今回のレビューで新たに実行した変更があれば、その場で行を足す。

## 運用の作法チェック（汎用PPCの定石。2026-08-23に `paid-ads` を読んで追加）

数字の異常が出ていなくても、**毎回この5点を確認する。** どれも8月の失敗に直接関係した。

### 1. 自動入札に切り替える前に、CVが50件以上溜まっているか

自動入札（コンバージョン最大化・目標CPA）は**過去のコンバージョンデータで学習する**。
データが足りないまま切り替えると、アルゴリズムが探索的に高値で入札して単価が跳ねる。

**2026-08の失敗**：切替時点のGoogleのCVは1.2件/日＝月36件。50件に届いていなかった。
結果としてCPCが¥98→¥307に。**切り替えるべきタイミングではなかった。**

→ 自動入札を提案・実行する前に、**直近30日のCV数を必ず数える。** 50未満なら手動またはCPC上限つきで待つ。

### 2. 既存顧客・最近のコンバーターを除外しているか

回数券保有者に「初回◯◯円」の広告を出し続けるのは、**費用の丸損**。

- Google：Customer Match の顧客リストを作り、`attach_user_list_to_ad_group` に `exclude=true` で紐づける
- 電話番号は CAPI 用の電話帳（Drive `32_顧客電話_マスタ`）が流用できる
- Meta：カスタムオーディエンスの除外設定

→ **未設定なら毎回指摘する。** 設定済みなら、リストが更新されているかを見る。

### 3. 直近3週間の変更回数が多すぎないか

`ops-change-log.md` の行を数える。**3週間に3回以上、学習をリセットする変更（クリエイティブ全面差し替え・
広告セット作り直し・入札戦略変更・LP切替）があれば警告する。**

学習が一度も安定しないまま数字を評価することになり、**何が効いたか永久に分からなくなる。**

**2026-08の実績**：8/01広告セット作り直し → 8/09入札変更 → 8/16 LP切替＋新RSA → 8/22入札リバート。
3週間で4回。この間の数字はどれも学習途上のもので、クリエイティブの良し悪しを判断できる状態ではなかった。

### 4. 予算変更は一度に20〜30%まで。次の変更まで3〜5日空ける

大きな予算変更は学習を中断させる。増額を提案するときは**刻みと間隔をセットで書く。**

例：¥6,000 → ¥8,000（+33%）は刻みすぎ。¥6,000 → ¥7,500（+25%）→ 4日後 → ¥9,000 とする。

### 5. フリークエンシー（広告疲労）を見たか

Metaは同じ人に繰り返し配信される。頻度が上がるとCTRが落ち、単価が上がる。
**週3〜5回を超えていたらクリエイティブのリフレッシュを検討する。**

## 検知したときの動き方

| 検知 | 最初に疑うもの |
|---|---|
| 費用↑なのに訪問↓ | 予算配分の変更、入札戦略の変更 |
| 特定媒体の訪問単価が1.5倍超 | その媒体の入札設定・ターゲティング・クリエイティブ差し替え |
| 安い媒体から高い媒体へ資金移動 | 配分判断の前提（単価を比較せずに決めていないか） |
| 新規の減少 > 訪問の減少 | 休業日、土日夜のシフト、HPB内の露出 |
| 成約率の低下 | 接客・担当者別のばらつき（ダッシュボードのスタッフ別で確認） |

## やらないこと

- **サロンボード（salonboard.com）へのプログラムからのアクセス**（規約で禁止）
- **顧客名・電話番号をレポートやリポジトリに書くこと**
- **数字の創作。** 取得できなかったものは「未取得」と書く
- **「気をつける」で終わらせること。** 見落としが起きたら、検知の仕組みを直す（このスキルとスクリプトを更新する）
